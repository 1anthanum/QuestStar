# Claude Code 接手系统：系统设计

> 这份文档解释**系统是怎么设计的、为什么这样设计**。
> 如果您只想知道**怎么操作**，请看 `TAKEOVER_GUIDE.md`。
> 两份文档建议一起读，但顺序无所谓。

---

## 一、要解决的问题

您要接手的项目通常处于以下状态：

- 大部分代码由前任 + LLM 协作写成
- 没有完整文档，也没有完整测试
- 关键设计决定散落在 commit message、聊天记录、和已经离开的人脑里
- 您可以读懂 Python，但前端是盲区
- 这个项目还在跑、还有用户、不能推倒重来

**核心矛盾**：您要在不完全理解代码的情况下，**安全地修改它、扩展它、维护它**。直觉的做法（"先把代码全读懂再动"）不现实——项目太大，时间太少，人脑容量不够。

**系统的设计目标**：把"靠人脑记住项目"换成"靠机制把项目知识沉淀在文件里、并让每次 Claude Code 会话自动继承"。

---

## 二、心智模型：五层结构

整套系统是五个层次叠在一起，从下到上越来越具体：

```
┌─────────────────────────────────────────────┐
│  五、子代理 (Subagents)                       │  专项任务的隔离上下文
│     code-reviewer, claude-md-keeper          │
├─────────────────────────────────────────────┤
│  四、斜杠命令 (Slash Commands)                │  您的"按钮"——一键触发完整流程
│     /takeover-scan, /refactor, /health-check │
├─────────────────────────────────────────────┤
│  三、CLAUDE.md 网络                           │  AI 自动加载的上下文
│     根 CLAUDE.md + 各子目录 CLAUDE.md         │
├─────────────────────────────────────────────┤
│  二、结构化文档                               │  长期记忆与契约
│     BEHAVIOR_SPEC, INVENTORY, ADR, ISSUES…   │
├─────────────────────────────────────────────┤
│  一、会话宪法                                 │  与 AI 的基本工作约定
│     固化在根 CLAUDE.md 中                     │
└─────────────────────────────────────────────┘
```

### 第一层：会话宪法（最底层、最稳定）

12 条工作约定，规定 Claude Code 在本项目中的行为边界——默认只读、单次改动 ≤ 30 行、必须读 CLAUDE.md、必须更新 CLAUDE.md，等等。

宪法**写在根 `CLAUDE.md` 里**，Claude Code 每次打开会话自动加载。这意味着您不需要每次手工粘贴宪法——它已经在那里了。

宪法是整套系统的"地心引力"。其他四层都假设 AI 在宪法约束下行动。

### 第二层：结构化文档（项目的长期记忆）

这些文档是项目的"客观真相"，存放在项目根目录或 `docs/`：

| 文档 | 作用 | 谁写谁读 |
|------|------|----------|
| `INVENTORY.md` | 文件清单 | AI 写，您审；下次 AI 读 |
| `DEPENDENCIES.md` | 模块依赖 | AI 写，您审；下次 AI 读 |
| `PLAIN_LANGUAGE_MAP.md` | 每个文件的中文一句话 | AI 写；您主要消费方 |
| `BEHAVIOR_SPEC.md` | 用户可见行为契约 | AI 起草，您补全；后续 AI 必读 |
| `ISSUES.md` | 已知问题清单 | AI 写，您审；重构时引用 |
| `docs/adr/*.md` | 历史决策记录 | AI 写，您审；AI 查阅 |

它们的共同特点是：**写一次、被读很多次**。文档是会话之间的"信使"。

### 第三层：CLAUDE.md 网络（AI 的导航系统）

Claude Code 的一个核心机制：**打开会话时自动读取当前工作目录及其各级父目录中的 `CLAUDE.md` 文件**作为上下文。

这意味着，如果您在 `src/api/` 目录下让 Claude Code 改一个文件，它会自动读到：
- `src/api/CLAUDE.md`（模块级上下文）
- `src/CLAUDE.md`（如有）
- `CLAUDE.md`（项目根，含宪法）

利用这个机制，您可以**让每个目录"自我介绍"**给未来的 AI：本目录是干什么的、对外契约是什么、内部实现有哪些约定、改动时要注意什么。

**根 CLAUDE.md 必须存在**。子目录 CLAUDE.md **按需创建**（判断标准在第三节"何时创建子目录 CLAUDE.md"——简而言之：当目录有 ≥3 个相关文件、对外有明确接口、且有非显而易见的约定时才建）。

### 第四层：斜杠命令（您的"按钮"）

斜杠命令存放在 `.claude/commands/<name>.md`，是您一键触发完整工作流的入口。例如：

- `/takeover-scan` — 全项目侦察扫描，产出 INVENTORY/DEPENDENCIES/PLAIN_LANGUAGE_MAP
- `/init-claude-md` — 生成根和子目录 CLAUDE.md
- `/build-safety-net` — 生成 BEHAVIOR_SPEC + E2E 测试 + CI
- `/diagnose` — 产出 ISSUES.md
- `/refactor <issue_id>` — 走完整单点重构流程
- `/new-feature` — 新需求七题门禁
- `/new-module` — 新模块易于改变设计门禁
- `/health-check` — 周例行健康检查
- `/claude-md-drift` — 月度 CLAUDE.md 漂移检查
- `/explain <path>` — 用中文解释某个文件或目录在做什么

斜杠命令的本质是**预制好的 Prompt 模板**。您每次不用手敲长长的指令——按一个键，AI 就知道该做什么、该用什么标准、该怎么报告。

### 第五层：子代理（隔离的小专家）

子代理（subagents）存放在 `.claude/agents/<name>.md`。它们的关键特点：**拥有独立的上下文窗口**。

这一层解决一个具体问题：**同会话袒护**。同一个 Claude Code 会话里写出来的代码，让它自己审查，它会袒护自己。要做真正的对抗式审查，必须把代码扔到一个**没有任何前期对话**的新上下文里。

本系统包含两个子代理：

- `code-reviewer` — 对抗式代码审查员。输入：git diff + 改动声称解决的问题。输出：六维审查报告。
- `claude-md-keeper` — CLAUDE.md 守护者。输入：本次改动的文件清单。输出：哪些 CLAUDE.md 需要更新、应该怎么改。

子代理通常被斜杠命令调用，您一般不直接和它们对话。

## 四、角色分工

这套系统假设三方协作，每方有明确的责任与不可越界的边界。

**您（人类）**：决策者 + 验收者
- 决定优先级、方向、取舍
- 审阅 AI 的输出（尤其 BEHAVIOR_SPEC、ISSUES、CLAUDE.md 的"项目禁区"段）
- 在 AI 越界或犯错时立刻叫停
- **不可外包的事**：业务理解、风险判断、最终拍板

**Claude Code（AI）**：分析员 + 结对程序员
- 扫描代码、生成文档、写代码、写测试、做审查
- 在斜杠命令和子代理框架内工作
- **不可越界的事**：擅自改方向、跳过验收、修改测试来掩盖问题、写未经同意的依赖

**文档与测试**：契约 + 自动化防线
- 文档承担"跨会话记忆"——这次 AI 写的契约，下次 AI 必须遵守
- 测试承担"自动化验收"——每次改动都自动检查行为是否被破坏

注意这三方的关系**不是层级**，而是**互相制约**。您信任 AI 但用文档和测试制衡它；AI 信任您但用宪法第 9 条（推荐 B 方案）来质疑您；文档和测试由您和 AI 共同维护。

## 五、信息流：上下文如何传递

要理解这个系统的精妙之处，最关键是理解**信息在哪里流动**。

### 单次会话内（横向）

```
您的需求
   ↓
（自动加载）根 CLAUDE.md → 涉及目录的 CLAUDE.md
   ↓
Claude Code 读取相关文档（BEHAVIOR_SPEC / ISSUES）
   ↓
执行改动
   ↓
更新 CLAUDE.md + BEHAVIOR_SPEC + 写测试
   ↓
Git commit
```

### 跨会话（纵向）

```
上次会话留下的：
  - 新的 CLAUDE.md 内容
  - 新写的 ADR
  - 更新过的 BEHAVIOR_SPEC
  - 新的测试
  - Git history
        ↓
本次新会话：
  - 自动加载 CLAUDE.md（继承上次结论）
  - 通过宪法第 11 条强制读取相关文档
  - 在上次的契约基础上继续工作
```

**关键设计原则**：会话之间不依赖"AI 记得"，只依赖**写在文件里的事实**。Claude Code 的会话本身是无状态的——但您的项目通过 CLAUDE.md 网络变成了有状态的。

## 六、设计如何防御已知失败模式

整套系统不是为了"让 AI 写出完美代码"——这做不到。它是为了**让 AI 的失败可预见、可发现、可回滚**。下表是十种常见失败模式与对应防御：

| # | 失败模式 | 系统对策 |
|---|---------|---------|
| 1 | AI 顺手清理无关代码 | 宪法第 4 条；`/refactor` 强制列出可改文件清单；验收清单第 5 条核对 git diff |
| 2 | 同会话袒护，找不出自己代码的问题 | 强制使用 `code-reviewer` 子代理在隔离上下文做对抗式审查 |
| 3 | 过度抽象、过度工程 | 宪法第 5 条；CLAUDE.md「替换难度自评」< 5 文件的硬指标 |
| 4 | 静默引入第三方依赖 | 宪法第 7 条；`/health-check` 每周对比 package.json / requirements.txt 的 diff |
| 5 | 修测试来掩盖代码问题 | 所有重构 Prompt 明示「禁止修复测试来掩盖问题」 |
| 6 | 自信地写错的代码（看起来对，实际错） | BEHAVIOR_SPEC + E2E 测试是最后防线；adversarial reviewer 找边界情况 |
| 7 | 任务边界蔓延（让做 A，做了 A+B+C） | 宪法第 4 条；斜杠命令在 Prompt 中明示「只改这些文件」 |
| 8 | 前端隐形变动 | 前端改动必须配套中文 E2E 测试，名称为"当用户...，应该..." |
| 9 | CLAUDE.md 与代码漂移 | 宪法第 12 条强制同步更新；`/claude-md-drift` 月度审查 |
| 10 | 过度切分模块（每个目录都建 CLAUDE.md） | 第三层"何时创建子目录 CLAUDE.md"的三条门槛 |

**重要**：这些防御**不是绝对的**。它们是统计意义上的过滤——降低事故概率，不消除事故。您仍然需要花时间做验收。如果某天您发现自己在跳过验收，请回滚当天工作并暂停（详见 `TAKEOVER_GUIDE.md` 紧急情况章节）。

## 七、本系统做不到的事（重要）

请在投入时间之前确认这些边界与您的处境兼容：

**不能替代代码审查能力**。`code-reviewer` 子代理能找出大部分常见问题，但它本身也是 LLM——会漏掉它训练数据里没见过的攻击模式或逻辑漏洞。

**不能保证安全**。涉及金钱、隐私、健康、未成年人的项目，本系统**不充分**。它能降低事故概率，但不能让您免于承担"应当读懂代码"的责任。这类项目请请人审。

**不能处理大型多人协作**。本系统假设单人维护或紧密协作的小团队。在 5+ 人项目中，CLAUDE.md 会出现合并冲突，BEHAVIOR_SPEC 会出现意见分歧——本系统不解决这些。

**不能用于法规重压力场景**。医疗、金融、航空、政务等需要正式可追溯审计的场景不要用。这套系统的"可追溯性"仅限于 Git 历史和 ADR，达不到合规标准。

**不能让您完全不学**。最起码您要看得懂 Python 控制流、能解读简单的 traceback、能区分 git status 和 git log。如果连这些都做不到，本系统的验收环节会落空，整个体系崩塌。

## 八、未来可能的扩展（不在初版范围）

如果您用熟了这套系统，可以考虑加入：

**Git 钩子（hooks）**：在 pre-commit 阶段自动检查"改动是否伴随 CLAUDE.md 更新"。这能把宪法第 12 条从"AI 自觉"升级为"机器强制"。

**CI 集成**：把 BEHAVIOR_SPEC E2E 测试搬到 GitHub Actions，每次 push 自动跑。

**多语言扩展**：当前模板偏 Python；将来可以追加 Node.js / Go 版本的命令文件。

**统计仪表盘**：跑一个本地脚本周期性统计「替换难度自评」「测试覆盖率」「ADR 数量增长」等指标，用 Streamlit 做成可视化页面。

**插件化**：将 `.claude/commands/` 打包成 Claude Code 插件，方便在多个项目间复用与版本管理。

这些不在初版交付物中。**先把基础跑通，再考虑加层**。

## 九、一个建议：何时考虑放弃这套系统

最后给您一个反向的诚实建议——**这套系统不是万灵药，也不是必须坚持**。在以下三种情况下，应当考虑停用：

第一，**您发现自己在三周内反复跳过验收**。这说明要么系统太重，要么您没时间——继续用反而会因为虚假的安全感造成更大事故。

第二，**项目长大到您一个人维护不动**。这时候应当找人合作或外包，本系统的单人假设已经不成立。

第三，**您学到了不再需要这套脚手架的程度**。这是好结果——表示您已经把这套实践内化成习惯了。这时候 CLAUDE.md 和 BEHAVIOR_SPEC 还有用，但斜杠命令可能显得冗余。

**承认这套系统的过渡性**，比把它当成"终极方法"健康。
