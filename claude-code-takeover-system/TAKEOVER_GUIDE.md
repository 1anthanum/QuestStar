# Claude Code 接手走查文档

> 这份文档解释**您具体要做什么、什么时候做、按什么顺序做**。
> 如果您想知道**为什么这样设计**，请看 `SYSTEM_DESIGN.md`。
> 假设您刚拿到一个不熟悉的项目，本文档带您从第 0 天走到稳定维护期。

---

## 〇、读前须知

**适用场景**

- 您接手一个已经在跑的项目（公司内部工具 / 您自己之前写的 / 别人交接给您 / 主要由 LLM 协助完成）
- 您会基础 Python，能读控制流和简单 traceback，但不读前端
- 项目规模在单人能维护的范围（粗略：< 20k 行代码 / < 50 个核心文件）
- 您打算长期维护这个项目，而不是改一次就丢

**必要前置**

- 项目在 Git 仓库里
- Claude Code 已安装并能在该项目目录打开
- 项目的所有依赖能在您本机跑起来（至少能启动）
- 至少一个测试框架可用（Python: pytest 或 unittest；前端: Playwright 或类似）

**时间预算**

| 阶段 | 投入 |
|------|------|
| Day 0 安装 | 15 分钟 |
| Day 1 侦察 | 半天 |
| Day 2 初始化 CLAUDE.md | 2-4 小时 |
| Day 3-4 建立安全网 | 1-2 天（视项目大小） |
| Day 5 诊断 | 2-3 小时 |
| Day 6+ 第一次重构 | 2-4 小时（第一次会慢） |
| 之后的每次重构 | 1-2 小时 |
| 每周维护 | 30 分钟 |
| 每月维护 | 1 小时 |

如果您一周只能挤出 4-5 小时，Day 0 到 Day 5 大约需要 **2-3 周**完成。**不要急**。

## 一、Day 0：安装

### 1.1 解压系统包

将系统 zip 包解压到您的项目根目录。解压后应当看到：

```
your-project/
├── CLAUDE.md             ← 新文件
├── .claude/              ← 新目录
└── docs/templates/       ← 新目录（如果 docs/ 已存在则合并）
```

### 1.2 验证 Git 状态

```bash
git status
git add CLAUDE.md .claude/ docs/
git commit -m "[setup] 安装 Claude Code 接手系统骨架"
```

> **重要**：在任何 AI 改动开始之前，先把这次"骨架安装"作为独立 commit，便于将来回滚。

### 1.3 验证 Claude Code 能读到 CLAUDE.md

打开 Claude Code 会话，发送：

```
请你列出你刚才自动加载的所有 CLAUDE.md 文件路径。如果只看到 CLAUDE.md（项目根），告诉我"只看到根 CLAUDE.md，无子目录 CLAUDE.md"。
```

正确响应应当列出至少根 CLAUDE.md。如果它说"没看到任何 CLAUDE.md"，说明 Claude Code 不在项目根目录打开，请关闭后在正确路径重开。

### 1.4 填充根 CLAUDE.md 的"项目特定的禁区"

打开 `CLAUDE.md`，找到「项目特定的禁区」段。**这一段 AI 不能替您填**，因为 AI 不知道您的项目历史。请您手动写入：

- 任何曾经出过事故的地方（"X 模块改动后曾导致数据丢失，所以..."）
- 任何业务约束（"用户名长度上限是 32，因为下游 CRM 有此限制"）
- 任何技术债务的"暂时不动"声明（"Y 文件代码很丑但在跑，**这次不重构**"）

如果暂时没有想到，**留空也比瞎填好**。漏写一条远比误导未来的 AI 安全。之后想起来随时补。

## 二、Day 1：侦察

### 2.1 准备工作

开一个新的 Claude Code 会话。第一条消息可以简短：

```
你好。请确认你已经读到根 CLAUDE.md 并复述其中的会话宪法十二条。
```

AI 应当列出十二条。如果漏掉任何一条，请它补全后再继续。

### 2.2 运行 `/takeover-scan`

```
/takeover-scan
```

这一步会产出三份文件到项目根：

- `INVENTORY.md` — 项目清单（目录结构、入口、依赖、异常文件）
- `DEPENDENCIES.md` — 模块依赖关系
- `PLAIN_LANGUAGE_MAP.md` — 每个源文件的中文一句话说明

预计耗时：5-15 分钟（视项目大小）。AI 期间会全程只读，不修改任何源代码文件。

### 2.3 您的审阅环节（不可外包）

通读三份文件，重点关注：

- `INVENTORY.md` 的「异常文件」段——里面提到的每个文件，您要么知道它为什么这样，要么标记为"待调查"
- `PLAIN_LANGUAGE_MAP.md` 的每一行——读不懂的就让 AI 改写得更通俗
- `DEPENDENCIES.md` 的「中心模块」和「孤岛文件」——这两类是后续重构的高价值目标

**强烈建议**：用文本朗读（TTS）把 `PLAIN_LANGUAGE_MAP.md` 朗读一遍。这是您"读项目"的方式。

### 2.4 Commit

```bash
git add INVENTORY.md DEPENDENCIES.md PLAIN_LANGUAGE_MAP.md
git commit -m "[侦察] Day 1 项目清单与依赖关系"
```

## 三、Day 2：初始化 CLAUDE.md 体系

### 3.1 运行 `/init-claude-md`

```
/init-claude-md
```

AI 会先**更新**根 CLAUDE.md（保留您之前填的"项目禁区"段），然后**逐个询问**您要为哪些子目录建立独立 CLAUDE.md。

它会用以下三条判断每个一级子目录是否值得有 CLAUDE.md：

- 包含 ≥ 3 个相关功能文件
- 对系统其他部分暴露明确接口
- 有非显而易见的约定或陷阱

至少满足两条才建。AI 会给您一个清单："建议建立 CLAUDE.md 的子目录：X, Y, Z；不建议建的：A, B"。

### 3.2 您批准清单

通常 AI 的判断是合理的，但请您过一遍。两类常见调整：

- AI 想给 `utils/` 建 CLAUDE.md，但您觉得太轻 → 拒绝
- AI 没给 `auth/` 建，但您知道这里有历史陷阱 → 强制建

### 3.3 逐个生成子目录 CLAUDE.md

对清单中的每个目录，AI 会依次提议内容、停下、等您审阅。

**关键审阅点**：

- 「对外契约」段是否真的只列了对外接口？私有函数不应该出现
- 「替换难度自评」段的数字是怎么得来的？让 AI 用 grep 验证
- 「本模块的常见陷阱」段应该留 `[由用户补充]` 让您之后填——AI 不应该猜

每个子目录 5-15 分钟，视模块复杂度。如果项目有 5 个独立 CLAUDE.md 目录，总耗时约 1-2 小时。

### 3.4 抽检与 commit

随机抽 2-3 个 CLAUDE.md，做一个小实验：

```
我刚做了一个 [无意义的小改动，例如改一行注释] 在 src/api/users.py。
请你按宪法第 11 条先读相关 CLAUDE.md，然后告诉我你读到了什么。
```

AI 应当报告"我读到 src/api/CLAUDE.md 中提到对外契约包括 X、Y、Z..."。如果它没读、或读错、或不提，说明 CLAUDE.md 的结构有问题，回去调整。

```bash
git add CLAUDE.md src/*/CLAUDE.md docs/templates/
git commit -m "[体系] Day 2 初始化 CLAUDE.md 网络"
```

## 四、Day 3-4：建立安全网（最关键的两天）

这是整套流程**唯一一个不能跳过的阶段**。没有安全网，所有后续重构都是赌博。

### 4.1 生成 BEHAVIOR_SPEC.md

```
/build-safety-net --phase=spec
```

AI 会扫描代码，生成一份初步的 `BEHAVIOR_SPEC.md`——所有用户可见行为的中文条目，每条采用「当 X，系统应该 Y」格式。

预计 30-60 分钟生成。生成完 AI 会停下，等您审阅。

**您的审阅是这个系统最关键的一次人工投入**：

- 删掉 AI 编造的行为（它对没把握的事容易凑数）
- 补全 AI 看不到的业务规则（来自您和用户的对话、历史 bug 报告、PRD）
- 在文件末尾的「待澄清」段填入您还不确定的条目，留待未来逐步确认
- 给所有"用户能做的事"和"用户不能做的事"都至少各一条

这一步可能要花您 **2-4 小时**，请认真。BEHAVIOR_SPEC 是后续所有 AI 重构的验收标准——它的质量决定整个体系的安全性。

### 4.2 生成端到端测试

```
/build-safety-net --phase=e2e
```

AI 基于 `BEHAVIOR_SPEC.md` 为每条规则生成一个端到端测试，放在 `tests/e2e/`。

预计耗时：1-3 小时，视规则数量。

**您的审阅**：

- 跑一遍所有测试。**全绿才能进下一步**。如果有失败，让 AI 调查原因——通常是 BEHAVIOR_SPEC 描述错了，需要修规格而不是改代码
- 抽检 2-3 个测试，确认测试名称是中文且您能读懂

### 4.3 生成 Python 特征测试（可选但推荐）

对每个关键 Python 模块：

```
/build-safety-net --phase=characterization --module=src/core/billing.py
```

这一步给"行为不能用端到端方式覆盖"的纯算法逻辑加保护网。

### 4.4 配置 CI

```
/build-safety-net --phase=ci
```

AI 生成 GitHub Actions（或您指定的 CI 工具）配置，每次 push 自动跑 lint + 测试。

### 4.5 Commit

```bash
git add BEHAVIOR_SPEC.md tests/ .github/
git commit -m "[安全网] Day 3-4 行为规格 + E2E 测试 + CI"
```

## 五、Day 5：诊断

### 5.1 运行 `/diagnose`

```
/diagnose
```

AI 基于已生成的所有文档，输出 `ISSUES.md`——问题清单，每条带类别、风险等级、修复成本。

预计耗时：30-60 分钟。

### 5.2 您的审阅（不可外包）

- 划掉 AI 误判的（把您故意保留的设计标成 bug）
- 添加 AI 看不到的（业务 bug、用户报告、生产事故）
- 重新调整风险等级（AI 不知道哪个功能对您最重要）

### 5.3 关键判断：是否要换栈

统计 ISSUES.md 中「前端」类别的占比。**如果 > 30%**，请暂停，先回答这个问题：

> 我应该逐条修这些前端问题，还是把整个前端换成更简单的栈？

参考 `SYSTEM_DESIGN.md` 中的"何时考虑放弃"段 + 之前手册附录 C 的技术栈选型表。如果决定换栈，本系统下一步是为新栈写一个迁移 ADR，然后用新栈重写——而不是修旧前端。

### 5.4 Commit

```bash
git add ISSUES.md
git commit -m "[诊断] Day 5 问题清单"
```

## 六、Day 6+：第一次重构（最重要的一次）

第一次重构的目的**不是修最大的 bug**，而是**走完整个流程一次**，建立您的肌肉记忆。

### 6.1 选最简单的高价值问题

从 ISSUES.md 中挑一项**风险中等、成本低**的（不要挑高风险的——第一次有风险）。理想选择：一个明显的小 bug，只影响一个 Python 后端文件。

### 6.2 运行 `/refactor <issue_id>`

```
/refactor #3
```

AI 会进入完整的六步流程：

1. 读相关 CLAUDE.md 并报告
2. 用中文说明改动方案（停下等您批准）
3. 实现改动（≤ 30 行 diff）
4. 跑所有测试（必须全绿）
5. 同步更新 CLAUDE.md + BEHAVIOR_SPEC（若需要）
6. 输出中文导读，等您验收

### 6.3 您的验收（按清单执行，不要跳）

- BEHAVIOR_SPEC 所有规则仍满足？
- 端到端测试全跑了？
- CLAUDE.md 同步更新了？
- git diff 完整看过？里面有没有 ISSUES.md 没提到的文件？
- 中文导读读懂了？

### 6.4 第三方审稿（开新会话）

打开**一个新的** Claude Code 会话（不是上一次的延续）：

```
/review-changes
```

AI 会问您粘贴 diff、问题描述、相关 CLAUDE.md。然后调用 `code-reviewer` 子代理给出对抗式审查报告。

把报告带回**原**会话给写代码的 AI 看，让它逐条回应。

### 6.5 Commit

```bash
git add -A
git commit -m "[重构] #3 修复 X 问题 - 因为 Y"
```

### 6.6 第一次完成后的反思

请认真回答自己以下三个问题：

- AI 在哪一步最让您不放心？
- 验收清单哪一项您最想跳？
- CLAUDE.md 的更新是否真的反映了改动？

如果有"我跳了步骤"的诚实答案，**今天到此为止**。明天重新做。

## 七、Week 1 回顾

第一周结束（连续做了 3-5 次重构后），用 30 分钟做回顾：

| 检查项 | 标准 |
|--------|------|
| 完成了几项 ISSUES？ | 3-5 项是健康的，少于 2 说明流程太慢，多于 7 怀疑跳了验收 |
| CLAUDE.md 被忠实更新了吗？ | 抽 2 个改过的目录，对比 CLAUDE.md 和实际代码 |
| 是否有一次跳过了某条验收？ | 诚实回答；如有，下周加强 |
| 第三方审稿报告里有真问题吗？ | 如果一次都没有，可能您的审稿 Prompt 太宽 |

调整后进入持续维护期。

## 九、新需求与新模块

项目跑起来后，您会有新功能要加。**永远不要直接让 AI 写**——先用门禁 Prompt：

```
/new-feature 我想加一个让用户导出订单为 PDF 的功能
```

AI 会停下来问您七个问题（详见手册 9.3 节）。这一步会挡掉大约 60% 的失控改动。

如果新需求需要新独立模块（新目录），用：

```
/new-module 我需要一个独立的 PDF 生成模块
```

这会强制 AI 先做"易于改变"设计——回答"封装了什么决策"、"替换难度自评 < 5 文件"等。

## 十、紧急情况处理

### 10.1 AI 改完代码您发现不对

立刻停。**不要让它"再修一下"**。先回滚：

```bash
git status
git diff
git checkout -- .          # 若尚未 commit
# 或
git reset --hard HEAD~1    # 若已 commit 未 push
```

然后开新会话，重新规划。

### 10.2 测试莫名其妙开始失败

不要让 AI 改测试。先用：

```
/explain tests/e2e/<失败的测试文件>
```

让 AI 用中文解释这个测试在做什么，然后用 `/diagnose` 的子流程查为什么失败。**测试是您的真相**，不要为了让代码"通过"而改测试。

### 10.3 您发现 AI 没更新 CLAUDE.md

立刻：

```
你刚才的改动违反了宪法第 12 条。请回滚本次 commit，然后重做并同步更新所有受影响目录的 CLAUDE.md。
```

如果这种情况频繁发生（一周内 ≥ 2 次），说明您和 AI 的对齐有问题。请：

1. 检查根 CLAUDE.md 中的宪法第 12 条是否仍然存在
2. 重启会话，开头让它复述宪法
3. 如果仍然漂移，记录下来作为 systemic issue，可能需要加 Git pre-commit hook（见 SYSTEM_DESIGN.md 第八节）

### 10.4 CLAUDE.md 已经漂移了一段时间

跑：

```
/claude-md-drift
```

AI 输出漂移报告。**您一条条审阅**，决定哪些更新文档、哪些需要先回滚代码再说。

不要让 AI 一次性自动修复全部漂移——那是让狐狸看鸡舍。

## 十一、什么时候停止使用这套系统

诚实自检：

**停止信号一**：连续三周您在跳验收。要么减负（每天只做半项重构），要么停用整个系统改用更轻的方法（仅 BEHAVIOR_SPEC + 测试，去掉 CLAUDE.md 网络）。

**停止信号二**：项目长到您一个人维护不动了（您每周加班还做不完）。这时该找人合作，本系统的单人假设不成立。

**停止信号三**：您学到不需要这套脚手架的程度。表现：您能凭直觉判断哪个改动安全、哪个不安全；您看 git diff 几乎不用 AI 解释；您写代码时自动想到"这能不能被替换"。这时候 CLAUDE.md 和 BEHAVIOR_SPEC 留下，斜杠命令可以裁掉。

**祝贺**——这才是这套系统的真正成功结局。

## 十二、一句话总结

**这套系统不让您变成程序员，但让您能安全地维护一个您不完全懂的项目**。它的全部价值依赖于您在每一次循环中诚实地走完验收。

走捷径就等于自欺。

如果某天您准备开始走捷径，请先回到 `SYSTEM_DESIGN.md` 第九节，决定要不要继续。
