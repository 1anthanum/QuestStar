# /new-module

用户要新增一个独立模块（新文件或新目录）。在写代码前，**必须**完成六步设计门禁。

## 六步设计门禁

### 1. 上下文确认

读项目根 `CLAUDE.md` + 最可能受影响的兄弟模块 `CLAUDE.md`。
告诉用户「已读 X、Y」。

### 2. 对外契约设计

这个模块的「对外契约」是什么？列出它将暴露的函数 / 类，每个的签名（输入、输出、副作用）。

**原则**：契约越窄越好。能不暴露就不暴露。

### 3. 设计决策识别

这个模块封装的「设计决策」是什么？即：哪个**未来可能改变的细节**藏在它内部，使外界不受影响？

如果回答是「没什么决策」——**那它不该是一个独立模块**。告诉用户，重新评估方案。

### 4. 替换难度自评

如果半年后我们想把这个模块整个删掉重写，会影响多少其他文件？

- **目标**：< 5 个文件被波及
- 如果你估计 ≥ 5，告诉用户「契约太宽，建议重新设计接口」

### 5. 目录归属

这个模块应该放在哪个目录？是否需要新建独立目录？

如果新建目录，按手册第 3.3 节判断它是否值得有自己的 `CLAUDE.md`：

- 包含 ≥ 3 个相关功能文件
- 对外暴露明确接口
- 有非显而易见约定

至少满足两条才建独立 CLAUDE.md。

### 6. 行为规格新增

`BEHAVIOR_SPEC.md` 中将新增哪些条目？草拟给用户看。

## 实施（用户批准后）

回答完六点**停下**。等用户说「按方案 X 实现」再开始执行：

1. 写代码（≤ 30 行 diff；超过请进一步拆分模块）
2. 写对应的端到端测试到 `tests/e2e/`
3. 创建 / 更新对应目录的 `CLAUDE.md`（按 `docs/templates/CLAUDE_subdirectory.md` 模板）
4. 更新根 `CLAUDE.md` 的「子目录地图」段（若新增了独立 CLAUDE.md 目录）
5. 更新 `BEHAVIOR_SPEC.md`
6. 把所有改动放在**同一个** git commit

## 完成后

输出 commit message 草稿（用户来执行 commit）：

```
[新模块] <模块名> - <一句话目的>

- 对外契约：…
- 设计决策：…
- 替换难度：影响 N 文件 / M 条规格
- 涉及 CLAUDE.md：…
```

并提示用户开新会话运行 `/review-changes`。
